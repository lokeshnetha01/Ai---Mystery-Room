# Implementation Decisions

## Project foundation
- The repository began with the authoritative `spec.md`; implementation is organized as npm workspaces for React/Vite and Express/Mongoose.
- The backend loads `backend/.env` by module-relative path so root and workspace commands use the same local configuration. Existing process environment variables take precedence. `.env` files remain ignored; `.env.example` files contain templates only.
- MongoDB health is reported from Mongoose state. A health response can succeed while database-backed routes return 503 if Atlas is not reachable.
- PowerShell users on Windows can run `npm.cmd` directly. The Node installation path may need to be added to the current terminal’s PATH.

## Frontend and API
- The Stage 2 preview case was removed when Stage 3 connected the UI to backend APIs. Public pages now use API case data; solution data stays on the server.
- Guest identity is a signed, HttpOnly, SameSite=Lax cookie. Mystery, note, and accusation operations scope queries to that session.
- Production frontend API requests use the relative `/api/v1` path. Vercel proxies this path to the Render API so the guest cookie remains same-origin and browser third-party-cookie restrictions do not break investigation sessions. The Render CORS origin must still be set to the exact Vercel production URL.
- The result endpoint requires an existing final accusation. The accusation stores whether it was correct; the result reads the original case solution rather than asking the model to decide again.

## Gemini structured generation
- Google’s current Gemini Interactions API is used for text structured output. It supports a top-level `response_format` with an `application/json` schema and keeps the story input separate from the system instruction. See [Gemini structured outputs](https://ai.google.dev/gemini-api/docs/structured-output) and [Interactions API overview](https://ai.google.dev/gemini-api/docs/interactions-overview).
- The previous legacy `generateContent` request produced Gemini 400 errors. A live minimal structured request passed with `gemini-3.8-flash` through Interactions.
- Gemini rejected the full Zod-generated schema as too complex for constrained decoding. The provider adapter now sends only structural types/properties/required fields and simple enums; Zod remains authoritative for IDs, timestamps, lengths, collection sizes, and semantic consistency after parsing. Corrections are bounded to three generation attempts.
- The Gemini generation schema requires all evidence-content keys, using empty strings, empty arrays, and zero as filler for irrelevant content. Before Zod validation, the server strips fillers and fields that do not apply to the evidence type. Required per-type fields still fail validation when absent. Person labels have short limits.
- A real generated case with 3 suspects, six evidence types, and five timeline events passed the full Zod and semantic consistency checks.
- `store: false` is set for Gemini interactions. User story text is sent to Google for generation as required by the feature; API keys and private solution data are never sent to the frontend.

## Evidence media
- Images and video are opt-in so text-only case generation remains usable. Google image generation and Gemini Omni video generation use provider adapters. If no provider and storage are configured, media is marked unavailable.
- Generated bytes are stored through signed Cloudinary uploads, not MongoDB. Public media URLs are restricted to HTTPS Cloudinary assets; no placeholder URL is treated as playable media.
- Suspect image prompts are removed from public suspect objects. Profile images use the same optional image/storage path as evidence.
- The current environment has no confirmed media provider or Cloudinary configuration, so live asset generation/storage remains unverified.

## Tests, operations, and current limits
- Vitest and Supertest cover validation, generation correction retries, session cookie behavior, private serialization, note session scoping, duplicate accusation handling, solution reveal gating, and media URL validation.
- The local environment has alternated between a successful Atlas connection and Mongoose server-selection failures. The latest Atlas connection check failed with `MongooseServerSelectionError`; its nested TLS cause was `ERR_SSL_TLSV1_ALERT_INTERNAL_ERROR`. The latest health response reported `database: disconnected`, so Mongo persistence and the full accusation workflow remain unverified live.
- No mock data is substituted in production. Live Gemini generation is verified; live API persistence and public-response secrecy still need a connected database.
- Vercel/Render targets are selected and their repository configuration is prepared. Provider projects, production credentials, deployment, and live verification remain incomplete.
